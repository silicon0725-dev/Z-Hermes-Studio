# Z Hermes Studio（ZHS）开发文档

-   文档类型：产品需求与技术设计基线（PRD + TDD）
-   版本：0.1.0-draft
-   状态：供实现前评审
-   产品名称：Z Hermes Studio（简称 ZHS）
-   首发平台：Windows、Linux、macOS
-   桌面技术栈：C#、.NET、Avalonia UI
-   初期 Agent Runtime：复用 ZCode 开源版，通过适配层接入
-   核心原则：先复用成熟运行时，再逐步自研差异化能力

------------------------------------------------------------------------

## 1. 项目概述

### 1.1 产品定位

Z Hermes Studio 是一款跨平台、原生 C# 桌面 AI 工作站。它以通用 Agent
Runtime
为执行基础，通过统一的项目、任务、记忆、工具、权限和产物体系，支持软件工程、文学创作、研究分析、游戏开发、UI/UX
设计及自动化工作流。

ZHS 不应被限制为 Coding Agent，也不应只是把现有 Web UI
包装成桌面窗口。产品要提供原生桌面体验，并允许不同领域的工作空间共享底层能力。

### 1.2 产品目标

1.  使用 C# 与 Avalonia 构建 Windows、Linux、macOS 跨平台桌面客户端。
2.  解决长会话打开慢、滚动卡顿、流式输出导致 UI 卡顿的问题。
3.  第一阶段复用 ZCode Runtime，不重写已有模型调用和工具执行能力。
4.  整合现有 Agent 集群、上下文管理、手柄控制三个插件。
5.  建立通用 Task Engine、Memory Engine、Policy Engine、Artifact Engine
    和 Extension Host。
6.  通过 Workspace 与 Capability Pack
    支持工程、写作、研究、设计等不同工作类型。
7.  保持模块边界清晰，使将来可以替换 Runtime 或逐步自研部分后端。

### 1.3 非目标

首期不做以下工作：

-   不一次性重写 ZCode 全部后端。
-   不要求所有模块都使用 C#；ZCode Runtime 可以继续运行在
    Node.js/TypeScript 进程中。
-   不把所有专业能力都实现成独立 Agent 产品或独立应用。
-   不在首期实现完整的图形化工作流编辑器。
-   不在首期强制引入向量数据库；先使用
    SQLite、FTS5、关键词和元数据过滤。
-   不承诺通过更换 UI
    框架就自动消除性能问题；性能必须以可重复基准测试验收。

## 2. 产品原则

### 2.1 通用内核、专业工作空间

-   **Core**：会话、任务、事件、权限、存储、扩展与 Runtime 适配。
-   **Workspace**：为某类工作提供布局、工作流、工具组合、产物编辑器和验证方式。
-   **Capability
    Pack**：可注册的工具、提示模板、工作流、领域规则、产物类型与验证器集合。
-   **Artifact**：工作产生的持久化成果，而不仅是聊天回复。
-   **Memory**：可追溯、按作用域检索的长期信息。
-   **Runtime Adapter**：将 ZHS 的稳定协议映射到 ZCode 或未来其他 Agent
    Runtime。

### 2.2 以用户确认的事实为准

用户明确确认的项目决策、小说设定和约束必须有状态标记。模型生成的推断不得自动覆盖已确认事实。对有破坏性的编辑、文件操作、外部发布和高风险命令，应按权限策略请求审批。

### 2.3 原始来源与摘要分离

摘要、提炼记忆和模型推断不能替代原始来源。研究结论应保存来源引用；创作设定应保留修改历史；代码修改应保留
diff 或版本控制记录。

### 2.4 UI 与执行解耦

UI 不直接访问 Agent
内部对象，不承担任务调度，不负责构造最终模型上下文。UI
通过版本化协议提交命令并接收状态事件。

## 3. 用户与核心使用场景

### 3.1 软件工程

-   分析代码仓库、规划任务、修改代码、运行测试、审查 diff。
-   将任务分派给 Planner、Explorer、Coder、Reviewer、Tester 等 Agent。
-   通过 Git Worktree 隔离并行任务。
-   保存架构决策、项目规则、失败记录和验证结果。

### 3.2 文学创作与世界观管理

-   维护作品设定、角色档案、地点、组织、时间线、剧情线、伏笔与章节。
-   生成或修订大纲和章节草稿。
-   比较版本、查看修改原因、进行人物动机与设定一致性检查。
-   区分已确认设定、候选设定、废弃设定和待确认问题。
-   保留创作决策记录，避免长对话中的设定漂移。

### 3.3 研究与技术决策

-   研究开源仓库、API、许可证、技术方案与竞品。
-   将结论、证据、来源、可信度和未解决问题整理为 Research Artifact。
-   生成技术评估、架构决策记录（ADR）和实施计划。
-   区分事实、推断、建议和未知信息。

### 3.4 UI/UX 与游戏开发

-   维护设计系统、设计 Token、组件规范、界面需求与验收标准。
-   连接现有 UI Designer、游戏引擎和相关开发工具。
-   维护玩法规格、资源清单、测试计划与版本记录。
-   让研究、设计、实现、审查和测试产物可以互相引用。

### 3.5 桌面交互与手柄

-   使用鼠标键盘完成全部核心功能。
-   支持 Xbox Controller 等手柄触发快捷浮层。
-   通过摇杆选择可用操作、模型或思考强度（取决于 Runtime 能力）。
-   任务结束时提供继续、审查、测试、提交说明等操作，并允许输入自定义指令。
-   手柄功能是交互方式，不是独立于任务系统的第二套状态机。

### 4.1 进程边界

建议首期至少划分两个进程：

1.  **ZHS Desktop**：C# /
    Avalonia，负责交互、展示、用户输入和客户端缓存。
2.  **ZHS Backend Host**：初期可由 ZCode 现有 Node.js
    进程及一个轻量适配服务承担，负责调用
    Runtime、执行工具、维护任务状态和提供事件接口。

不要求第一版就把所有 Core
模块独立部署。可以先在同一后端进程中按模块组织，等确有隔离、扩展或性能需要时再拆分。

### 4.2 Runtime Adapter

定义与具体 Runtime 无关的接口，例如：

``` csharp
public interface IAgentRuntime
{
    Task<AgentHandle> StartAsync(
        AgentTaskRequest request,
        CancellationToken cancellationToken);

    Task SendMessageAsync(
        AgentHandle handle,
        string message,
        CancellationToken cancellationToken);

    Task InterruptAsync(
        AgentHandle handle,
        CancellationToken cancellationToken);

    Task<AgentStatus> GetStatusAsync(
        AgentHandle handle,
        CancellationToken cancellationToken);
}
```

该接口是 ZHS 的设计目标，不代表 ZCode 当前已经提供相同
API。实现前必须根据锁定版本的实际源码完成适配映射。

## 7. 长对话性能设计

长对话性能是首期 P0
目标。历史加载、滚动和流式输出必须分别测量、分别优化。

### 7.1 历史消息加载

-   打开会话时先加载元数据和最近一页消息。
-   初始页面大小建议为 40--80 条，后续根据基准测试调整。
-   使用稳定游标分页，例如 `(session_id, sequence)`，避免深页 `OFFSET`。
-   较大的工具输出、代码输出和附件使用独立内容记录或文件引用。
-   更早历史在用户向上滚动时异步加载。
-   支持取消过期查询，避免切换会话后旧结果覆盖当前界面。
-   对常用会话可缓存最近一页和解析后的轻量消息模型。
-   首期明确数据库的唯一写入所有者，避免 Desktop 与 Backend
    双写产生不一致。

### 7.2 消息列表与滚动

-   消息列表必须处于有界高度容器中，确认 Avalonia 虚拟化实际生效。
-   使用虚拟化列表，不为整个历史会话创建控件。
-   消息采用稳定 ID，避免因集合重建而丢失滚动位置。
-   普通文本、代码、工具调用、错误、审批和附件使用不同的轻量消息模板。
-   维护滚动锚点；顶部插入历史消息后，用户当前可见内容不能突然跳动。
-   Markdown、代码高亮和附件预览按需渲染。
-   大型工具输出默认显示摘要和展开入口。
-   限制动画、模糊、阴影和过深的控件嵌套。
-   用户滚动离开底部后不强制跟随新消息，提供"跳到最新消息"入口。

### 7.3 流式输出

建议的数据路径：

``` text
Runtime events
    ↓
Protocol decoder
    ↓
Bounded Channel
    ↓
Event coalescer
    ↓
UI dispatcher / frame scheduler
    ↓
Update active message only
```

实现规则：

1.  连续文本增量可以合并，但工具调用、审批、任务终止等结构化事件不能被丢弃。
2.  不对每个 Token 重新解析完整 Markdown 或刷新整个消息集合。
3.  在生成期间使用轻量文本展示；代码高亮和复杂 Markdown
    处理可以局部更新或延迟。
4.  事件队列必须有界，设置背压和合并策略，防止慢 UI 导致内存无限增长。
5.  取消、错误、审批和完成事件应有明确优先级，不能被普通文本淹没。
6.  每条消息的增量更新都应校验 `messageId` 和 `sequence`，避免乱序覆盖。
7.  记录队列深度、批处理大小、UI 提交延迟和丢弃/合并计数。

### 7.4 建议性能验收目标

以下是首轮工程目标，不是已测得的性能承诺。必须在固定硬件、Release
构建和可重复数据集上验证。

  指标                          初始目标
  ----------------------------- ------------------------------------
  热缓存会话首屏可交互时间      P95 ≤ 500 ms
  未缓存会话首屏可交互时间      P95 ≤ 1.5 s
  60 FPS 目标下正常滚动帧时间   P95 ≤ 16.7 ms
  UI 主线程单次同步工作         目标 ≤ 8 ms
  流式输出期间 UI 更新          约 30--60 次/秒，按设备调节
  会话切换                      旧请求可取消，旧结果不得覆盖新会话
  大会话加载                    按页加载，不一次性构建全量控件树

测试数据集至少包含 1,000、10,000、50,000 条消息三种规模，并覆盖
Markdown、代码块、工具调用、长输出、附件和异常事件。分别记录冷/热启动、数据库读取、解析、布局、内存峰值和
GC 暂停。

## 8. 通信协议与事件模型

### 8.1 协议要求

-   所有请求、响应和事件均带协议版本。
-   请求有唯一 `requestId`；事件有唯一 `eventId`。
-   事件携带 `sessionId`、`sequence` 以及必要的 `messageId`、`taskId`。
-   错误使用结构化错误码，不依赖自由文本判断。
-   支持请求取消、超时、连接重建和状态快照。
-   本机通信需要认证或等效安全边界，不能因为只监听本机就假设没有安全风险。
-   不把 API Key、访问令牌或敏感文件内容写入普通日志。

### 8.2 初期事件类型

-   `session.snapshot`
-   `message.created`
-   `message.delta`
-   `message.completed`
-   `message.failed`
-   `tool.started`
-   `tool.completed`
-   `task.status_changed`
-   `approval.required`
-   `artifact.created`
-   `artifact.updated`
-   `runtime.disconnected`
-   `runtime.reconnected`

### 8.3 断线恢复

客户端保存最后确认的事件序号。重新连接后，先尝试续传；如果后端不再保留所需事件，则获取当前状态快照，再恢复订阅。重复事件应通过
`eventId` 或序号幂等处理。

## 9. 核心模块职责

### 9.1 Session Service

负责会话生命周期、会话元数据、消息关联与运行状态。聊天记录是历史事实，不等同于模型每次调用使用的上下文。

### 9.2 Task Engine

负责任务图、依赖、并行度、重试、取消、恢复和任务产物关联。任务状态需要持久化，不能只存在内存中。

### 9.3 Memory Engine

采用分层检索：

1.  项目、领域、时间、实体等元数据过滤。
2.  关键词检索与 SQLite FTS5。
3.  需要时再评估向量检索。

记忆类型包括全局偏好、项目事实、任务进度、领域规则和决策记录。每条记忆应有来源、作用域、可信状态、创建时间和修订历史。

### 9.4 Policy Engine

为文件读写、Shell、网络、凭据、外部发布和破坏性操作设置权限。支持按操作风险自动执行、需要审批和禁止执行三类策略。审批记录与实际执行结果关联。

### 9.5 Artifact Engine

统一管理工作成果。Artifact 具有稳定
ID、类型、版本、来源、项目归属、依赖和修改历史。专业类型可以注册专属编辑器、导入器、导出器和验证器。

### 9.6 Extension Host

提供插件、Skills、MCP 和 Capability Pack
的发现、注册、版本、权限、启停与诊断。扩展必须声明所需权限和兼容的协议版本。首期先适配
ZCode 已有扩展能力，不重复实现已有机制。

### 9.7 Runtime Adapter

负责将 ZHS 的会话、任务、工具和事件模型映射到 ZCode
Runtime。适配层不得把 ZCode 私有类型泄漏到 Domain 或 UI 层。

## 10. Artifact 与 Workspace 设计

### 10.1 Artifact 通用字段

``` json
{
  "id": "artifact_stable_id",
  "projectId": "project_id",
  "type": "document",
  "title": "示例产物",
  "version": 1,
  "status": "draft",
  "createdAt": "ISO-8601 timestamp",
  "updatedAt": "ISO-8601 timestamp",
  "sourceRefs": [],
  "relatedArtifactIds": [],
  "contentRef": "storage_reference"
}
```

此 JSON 是概念示例，正式 Schema 需要版本化。大型内容不应全部内嵌在列表
API 的响应中。

### 10.2 首期 Artifact 类型

-   `document`：技术文档、小说章节、研究报告。
-   `code-change`：文件修改、补丁和 diff 引用。
-   `research`：来源、证据、结论与待确认问题。
-   `narrative-entity`：角色、地点、组织、世界规则、剧情线。
-   `design-spec`：设计 Token、组件规范和界面需求。
-   `workflow-run`：任务图、执行日志和验证结果。

### 10.3 Workspace API

Workspace 负责注册：

-   导航入口和页面布局。
-   可用的 Artifact 类型与编辑器。
-   Capability Pack。
-   工作流模板。
-   领域记忆检索策略。
-   验证器与导入/导出器。

Workspace 不应直接绕过 Core 操作 Runtime、数据库或权限系统。

### 10.4 首期工作空间

1.  **General**：通用对话与产物。
2.  **Engineering**：代码、测试、diff、仓库任务。
3.  **Writing**：作品、章节、角色、设定、时间线、版本对比。
4.  **Research**：来源、证据矩阵、结论、技术比较。
5.  **Design**：设计规范、Token、组件和原型引用。
6.  **Game Development**：玩法规格、资源、代码与测试任务。

MVP 不必全部完成。先实现 General、Engineering 的基本闭环，并验证
Artifact API 可以承载 Writing 与 Research 的核心数据。

------------------------------------------------------------------------

## 11. 数据持久化与所有权

必须在实施前确定各类数据的唯一事实来源。

  -------------------------------------------------------------------------------------
  数据                    首期建议所有者                   说明
  ----------------------- -------------------------------- ----------------------------
  Runtime 内部会话状态    ZCode Runtime                    通过 Adapter 暴露稳定视图

  ZHS 项目与 Workspace    ZHS Backend                      统一管理
  元数据                                                   

  Task Graph 与执行检查点 ZHS Task Engine                  持久化恢复状态

  Artifact 元数据与版本   ZHS Artifact Engine              内容可使用文件或数据库引用

  Memory 与 FTS5 索引     ZHS Memory Engine                原始来源单独保留

  UI 临时状态与缓存       ZHS Desktop                      可重建，不作为权威数据

  API 凭据                操作系统安全存储或后端受控存储   不写入普通配置、日志或
                                                           Artifact
  -------------------------------------------------------------------------------------

若 ZCode 当前已有会话数据库，先通过只读适配或迁移方案复用，不要让 C# UI
与 Node.js
后端同时直接写同一套表。需要迁移时，应有备份、版本迁移和回滚策略。

## 12. 安全、权限与供应链

-   对 ZCode 上游固定版本或 commit，并记录上游来源。
-   审查上游许可证、NOTICE、依赖许可证和再分发要求。
-   为插件与 MCP 声明权限，避免默认授予任意文件、Shell 和网络访问。
-   本地 IPC 不应暴露到非预期网络接口。
-   日志默认对令牌、凭据、敏感路径和大段文件内容脱敏。
-   文件修改、执行命令、网络访问和发布操作应有审计记录。
-   高风险操作使用显式审批，审批内容应包含动作、目标、影响范围和参数摘要。
-   任务失败重试应有次数上限、退避策略和幂等约束。
-   自动清理 Git 分支或 Worktree
    时，必须检查未提交修改、未合并提交和关联任务状态。

------------------------------------------------------------------------

## 13. 三个既有插件的整合方案

### 13.1 Agent 集群插件

先保留现有实现，通过 Adapter 映射到 Task Engine。逐步统一 Agent
注册、启动、消息、取消、状态、输出产物和故障恢复接口。不要在第一阶段为了
UI 集成而彻底重写集群调度器。

### 13.2 上下文管理插件

保留现有 SQLite、FTS5、留痕和非破坏性记忆思路。先定义统一 Memory API
与来源引用，再逐步把插件内部模型迁入 Memory
Engine。确认过的项目事实与模型推断必须区分。

### 13.3 手柄控制插件

把手柄事件映射为与鼠标键盘相同的应用命令，不直接操作 UI
控件内部状态。快捷浮层、模型选择、思考强度、任务结束选项都通过统一命令与权限检查执行。

## 14. 实施里程碑

### M0：源码盘点与架构冻结

交付物：

-   固定 ZCode 上游版本并检查许可证。
-   绘制 Runtime、会话、Provider、插件和事件的数据流。
-   盘点三个插件的依赖、入口、存储和调用方式。
-   完成 ADR-0001 至 ADR-0004。
-   确定数据库写入所有者和本地通信方案。

验收：所有关键依赖和进程边界都有源码证据，不根据 README 猜测内部 API。

### M1：原生桌面垂直切片

交付物：

-   Avalonia 桌面应用。
-   会话列表、发送消息、取消生成、流式显示。
-   Runtime Adapter 最小实现。
-   基础协议版本与错误模型。
-   Windows、Linux、macOS 构建流水线。

验收：不使用 WebView 即可完成基本聊天；连接断开时界面不崩溃。

### M2：长对话性能

交付物：

-   SQLite 游标分页或适配现有会话存储。
-   消息列表虚拟化。
-   历史加载与滚动锚点。
-   有界流式事件队列和增量消息更新。
-   1k/10k/50k 消息压力测试与性能报告。

验收：分别测量历史加载、滚动和流式输出；达到第 7
节的初始目标，或记录可复现的差距与优化计划。

### M3：统一任务与插件

交付物：

-   Task Engine 最小版本。
-   集群插件 Adapter。
-   Memory API 与上下文插件 Adapter。
-   手柄命令适配。
-   任务状态面板和执行日志。

验收：同一任务可以被创建、执行、取消、查看结果，并将产物关联回项目。

### M4：Artifact 与项目系统

交付物：

-   Project、Artifact、版本和来源引用。
-   文档与研究 Artifact。
-   基本差异查看和版本恢复。
-   General、Engineering、Research 的初始 Workspace。

验收：工作成果不只存在于聊天文本中，可以独立打开、检索和追溯来源。

### M5：Writing Workspace

交付物：

-   作品、章节、角色、设定、时间线的领域模型。
-   已确认/候选/废弃设定状态。
-   大纲到章节草稿的可配置工作流。
-   章节版本对比与设定一致性检查。
-   用户审批和修订记录。

验收：能够维护一个多章节作品，修改设定时能展示相关引用和潜在影响，不自动覆盖已确认设定。

### M6：扩展生态与产品化

交付物：

-   Capability Pack 清单与兼容性检查。
-   插件权限和诊断。
-   崩溃恢复、升级、迁移和日志导出。
-   三个平台的安装包与基本验收。

验收：安装后可独立运行；扩展失败不会破坏核心会话和项目数据。

## 15. 测试策略

### 15.1 单元测试

覆盖领域状态转换、分页游标、事件排序、幂等处理、权限决策、Artifact
版本和记忆作用域。

### 15.2 集成测试

覆盖 Runtime
Adapter、连接断开与恢复、任务取消、数据库迁移、插件启停和审批流程。

### 15.3 性能测试

-   固定消息数据集与机器配置。
-   分开测试冷启动、热启动和会话切换。
-   模拟高频文本增量和大量工具事件。

-   结果记录环境、commit、构建模式和原始数据，禁止只保留平均值。

展示、快捷键、剪贴板、文件路径、系统主题、打包和升级。平台特有能力通过
`IPlatformServices` 等接口隔离。

## 16. 风险与应对

  ------------------------------------------------------------------------------------------
  风险                                应对
  ----------------------------------- ------------------------------------------------------
  ZCode 内部 API 变化                 固定上游版本；将所有依赖集中在 Runtime
                                      Adapter；建立适配器契约测试

  C# UI 重写后仍卡顿                  先建立基准测试；区分数据库、解析、布局和事件传输瓶颈

## 17. 首期 MVP 的明确范围

首期必须交付：

-   C# / Avalonia 原生跨平台桌面壳。
-   ZCode Runtime Adapter。
-   基本聊天、取消、流式消息与会话切换。
-   长会话分页、虚拟化和性能埋点。
-   版本化本地 RPC 与断线恢复。
-   基础项目模型、SQLite 持久化与诊断。
-   三个现有插件的接入边界与至少一个端到端整合场景。

首期可以延后：

-   完整图形化 DAG 编辑器。
-   多人协作和云端同步。
-   全功能向量记忆。
-   全部 Artifact 专业编辑器。
-   完整写作 IDE。
-   自研模型推理或完全替换 ZCode Runtime。

**MVP 完成定义：**
用户能在原生桌面端完成一次完整会话；大历史按需加载；流式生成期间 UI
保持响应；断线后可以恢复状态；已有插件能够通过受控接口参与任务；代码、文档或研究结果可以作为独立产物保存。

## 18. 开发约定

-   使用 ADR 记录架构决策，重要决策变更必须更新对应 ADR。
-   公共接口必须有 XML 文档、错误语义和取消行为说明。
-   所有后台 I/O 都必须支持取消和超时。
-   不允许把 Runtime 私有类型泄漏到 Domain、Presentation 或 Protocol
    公共模型。
-   每个新增能力都必须有最小测试与诊断信息。
-   性能优化必须有基准数据支持。
-   任何数据库 Schema 变更都必须提供迁移与失败恢复方案。
-   对生成式内容，必须保留来源、版本或用户确认状态中适用的元数据。
-   依赖升级、上游同步和扩展协议升级应分别评估，避免一次提交混合多类风险。

------------------------------------------------------------------------

2.  对三个既有插件做依赖与接口盘点。

系统能够持续完成不同领域的工作：执行任务、维护项目状态、积累可追溯记忆，并交付可以继续编辑和验证的成果。
